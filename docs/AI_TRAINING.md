# MAZEWARD VERSUS 対戦AI — 設計と運用

対戦モードの AI を強化学習で作るための一式。Minecraft サーバーを起動せずに
**Python 側でルールを再現**して学習し、バランス診断まで同じ数値定義から行う。

```
ai/
  balance.py             全数値の単一の真実。調整者が触るのはここだけ
  sync_balance.py        balance.py と Java enum の突き合わせ（テキスト解析）
  selfcheck.py           Python 環境が Java と同じ挙動をするかの検査
  balance_analyzer.py    バランス診断・推奨値の出力
  policy.py              方策ネットワーク（1 バックボーン + 複数ヘッド）
  train.py               PPO + リーグ自己対戦 + 模倣学習
  trainer_pb.py          GUI との窓口（JSON ログ / 進捗行 / 終了コード）
  mc_brain.py            学習した方策を Minecraft へ貸し出すブリッジ（§6）
  mc_parity.py           ブリッジの観測 == 学習の観測 の検査（§6）
  mazeward_env/          環境本体
    balance 非依存: grid.py pathfinder.py shapes.py rules.py
    ルール:        combat.py env.py observation.py reward.py
    基準ボット:    bots_heuristic.py
    ブリッジ:      mc_snapshot.py（実ゲームの状態 → 学習と同じ観測）
  models/                チェックポイントと学習ログ（ローカル正本）
dashboard/               GUI（Flask + SSE）
```

Minecraft 側（`src/main/java/dev/antigravity/mazeward/ai/`）は
`MatchSnapshot`（事実の送信）・`BrainClient`（接続）・`AiDirector`（適用）・
`HeuristicPolicy`（ブリッジが無いときの相手）の 4 つだけ。**観測は持たない**（§6）。

---

## 1. なぜこの設計にしたか

### 1-1. 迷路・タワー・送りを 1 つの方策で学ぶ

**3 つを別々のモデルに分けない。** この 3 つは

- カード（迷路）… 30 秒に 1 枚しか来ない。壁は撤去できない
- コイン（タワー）… 設置・強化に使う
- コイン（送り）… **タワーと同じ財布**

という形で、同じ資源を奪い合っている。分けて学習させると、それぞれが
「自分の担当だけ最適」に振る舞い、**配分という肝心の判断が誰にも学習されない**。

そのため:

- バックボーンは 1 つ（盤面 CNN ＋ スカラー MLP ＋ 相手エンコーダ）
- ヘッドだけ分岐（`type` / `card` / `tower` / `cell` / `unit` / `spec` / `send`）
- **価値関数は 1 つ**

「塔だけ学習」「送りだけ学習」といったモードは**コードに存在しない**。
`train.py` の学習ループは 1 本しかなく、行動種別は `type` ヘッドが選ぶ
1 つの分布から引かれる。

### 1-2. 観測は「比」で渡す（数値変更に強くする鍵）

「弓塔のコストは 30」を覚えた方策は、コストを 35 に変えた瞬間に壊れる。
そこで `observation.py` は絶対値をほとんど入れず、

- `コイン / 次の送りコスト`、`最安タワーコスト / インカム`（＝何秒待ちか）
- 塔ごとの `実効DPS / 総コスト`、`射程 / 盤面サイズ`
- 送りごとの `HP / コスト`、`リーク効用 / コスト`、`インカム増 / コスト`
- `自陣DPS x 10秒 / 湧いている敵の合計HP`（＝溶けるか漏れるか）

を渡す。**ドメインランダム化（±20%）と対で効く。** 片方だけでは足りない。

### 1-3. 相手は「実際に見える情報」を全開示

実ゲームでは相手の島へ飛んで見に行けるので、迷路の形・タワーの配置・強化状態は
実質公開情報。チャットに送り履歴も流れる。だから

- **見える**: ライフ / ライフ上限 / 脱落 / 経路長 / タワー数と平均Lv /
  射程カバレッジ / 送り履歴 → そのまま渡す
- **見えない**: コイン / インカム / ストック / 手札 → **送り履歴からの推定**のみ

部分観測にすると PPO が「見えない相手の状態の推定」まで同時に学ぶことになり、
収束が遅くなる。取れる情報は全部渡して MDP に近づけている。

人数が 2〜8 で変わるので、相手は**最大人数ぶんの固定スロット + マスク**にし、
平均と最大の両方でプーリングする（平均＝全体の状況、最大＝いちばん危ない 1 人）。

## 2. 環境の実装方針（速度）

`ai/mazeward_env/` は **1 つずつ島を回さない**。`B = 環境数 x 人数` 個の島を
1 本の numpy 配列に詰め、塔 x 敵の距離行列を一括で作る。

プロファイル（cProfile）で効いた順:

| 対策 | 効果 |
|---|---|
| `enemy_positions` を経路スロット単位に分割 | **約 3 倍**（最大のボトルネックだった） |
| 敵の枠を毎ステップ前詰め（`compact_enemies`） | 距離行列の幅が実際の敵数まで縮む |
| 壁の変更と塔の変更で再計算を分ける | 塔設置で Theta* を引き直さなくなった |
| 塔マスクを正規化セル集合でキャッシュ | 36 回 → 6 回 |

実測: **約 4,700 島ステップ/秒**（RTX 3050 / 12 コア、1 ステップ = ゲーム 1 秒）。

**Numba / C++ 化には進んでいない。** 測った結果、律速は Theta* と観測の組み立てで、
どちらも「呼ぶ回数を減らす」ほうが効いたため。必要になったときは
`Grid → combat → observation` を同じ `step`/`reset` API で差し替えられるようにしてある。

### 実ゲームとの意図的な差（すべて `combat.py` の冒頭に列挙）

1. 1 サブステップ（4 tick）内で同じ塔が複数回撃つとき、狙いは 1 回しか選び直さない。
   **DPS は完全に保たれる**（撃てる回数を `floor(蓄積 / クールダウン)` で数え、余りを繰り越す）
2. 壁を置いたあとの再経路は、敵ごとの Theta* ではなく**新しい折れ線への最近点投影**
3. 敵オーラ（回復・庇護）と妨害は 20 tick ごとの離散適用ではなく毎サブステップの連続適用。
   1 秒あたりの量は同じ
4. 瞬移の跳び先探索は 0.5 ブロック刻みではなく 64 分割

`selfcheck.py` が、撃破までの tick 数・漏れまでの tick 数・撃破報酬・
経済・能力の発動・不変条件（敵が壁の中に入らない等）を機械的に検査する。

## 3. 学習

```bash
cd ai
python train.py                 # 環境変数で設定（下表）
```

| 環境変数 | 意味 | 既定 |
|---|---|---|
| `MAZEWARD_MAX_GENS` | 回す世代数 | 20 |
| `MAZEWARD_NUM_ENVS` | **同時試合数**（0 = 自動） | 自動 |
| `MAZEWARD_ROLLOUT` | PPO 更新 1 回ぶんのステップ数 | 96 |
| `MAZEWARD_GEN_EARLY_MIN` | 完了を待つ上限（ゲーム内・分） | 30 |
| `MAZEWARD_GEN_MAX_MIN` | 打ち切り（ゲーム内・分） | 60 |
| `MAZEWARD_GEN_FINISH_EARLY` | 上限までに求める完了率 | 1.0 |
| `MAZEWARD_GEN_FINISH_LATE` | 上限を過ぎたあとの完了率 | 0.9 |
| `MAZEWARD_RANDOMIZE` | ドメインランダム化の強さ | 0.20 |
| `MAZEWARD_BC_BATCHES` | 模倣学習のバッチ数 | 60 |
| `MAZEWARD_EVAL_EVERY` | 何世代ごとに評価するか | 5 |
| `MAZEWARD_CURRICULUM` | カリキュラム（0 で無効） | 1 |
| `MAZEWARD_ENTROPY` | エントロピー係数 | 0.02 |

### 世代の区切り — ゲーム内時間と試合完了率で決める

**1 ステップ = 20 tick = ゲーム内 1 秒。** だから「この世代でゲーム内何分ぶん
回したか」は常に正確に出せる（`game_minutes` / `game_hours_total`）。

以前は固定ステップ数（160 = ゲーム内 2 分 40 秒）で切っていた。すると
1 試合（4〜12 分）の途中で世代が変わり、**勝敗を 1 度も含まない世代**ができて
`games_finished: 0` が交互に並んだ。いまは試合の切れ目で区切る。

```
ゲーム内 30 分以下 かつ 完了率 100%   → 次の世代
ゲーム内 30 分以上 かつ 完了率  90%   → 次の世代
ゲーム内 60 分 超え                   → 完了率に関わらず打ち切り
```

「完了率」は **1 試合以上を終えた同時試合の割合**。決着率（脱落者が出た割合）
とは別物なので、指標も `match_completion` と `finish_rate` に分けてある。

メモリのため、1 世代は `ROLLOUT` ステップの塊に分けて回し、**塊ごとに PPO 更新**
する（ゲーム内 1 時間ぶんを一度に溜めると観測だけで 2GB を超える）。
1 世代の更新回数は `updates` に記録される。

実測（16 同時試合）: 基礎カリキュラム（4 分マッチ）で
**ゲーム内 4.0 分 / 更新 2 回 / 決着 16 局 / 実時間 12 秒**。
全世代で `games_finished > 0` になった。

### 学習時間の見積もり（実測）

RTX 3050 (8GB) / 12 論理コア、`ROLLOUT=160` での実測値。

| 条件 | 島ステップ/秒 | 1 世代 | 備考 |
|---|---|---|---|
| 32 試合 x 2 人（64 島） | 約 4,700 | **約 10〜14 秒** | 基礎カリキュラム（4 分マッチ） |
| 64 試合 x 2 人（128 島） | 約 4,700 | 約 20〜26 秒 | 線形にスケールする |
| 評価（`EVAL_EVERY` 世代ごと） | — | 約 60〜90 秒 | 12 分マッチを 5 種類（vs ランダム / vs 過去最強 / 2・4・8 人） |

40 世代（評価 5 回）で **おおよそ 15 分**。実戦レベルまで持っていくには
数百〜数千世代が要るので、その規模では Colab などで回すことを想定している
（`trainer_pb` が Drive への永続化に対応済み）。

**AMP と `torch.compile` は入れていない。** プロファイルの結果、時間の大半は
CPU 側の環境（Theta* と観測の組み立て）で、GPU は方策の前後だけで遊んでいる。
GPU 側を速くしても全体はほとんど変わらないため、先に環境側を詰めた。
ネットワークを大きくするか環境を C++ 化したら、そのときに入れる。

### 並列環境数の決め方（トレーナー契約からの逸脱）

契約の VRAM 表は「環境が GPU 上で回る」前提。**この環境は numpy で CPU 側を
回している**ので律速は CPU で、GPU は方策の前後だけ。そのため VRAM ではなく
論理コア数から決めている（`trainer_pb.auto_num_envs`）。逸脱の理由はここに明記した。

### カリキュラム — `max_ticks` がいちばん効く

1 試合 20 分（1200 ステップ）だと、128 ステップのロールアウトに**勝敗が 1 度も
入らない**。実際に 8 世代回して `games_finished: 0` のまま伸びなかった。
序盤は 4 分まで詰めて、1 世代のあいだに必ず決着を経験させる。

| 段階 | 盤面 | 人数 | 送り | 試合長 |
|---|---|---|---|---|
| 基礎 | 15x15 | 2 | 2 種 | 4 分 |
| 拡張 | 17x17 | 2 | 6 種 | 6 分 |
| 多人数 | 21x21 | 2-4 | 全種 | 8 分 |
| 完全 | 21x21 | 2-8 | 全種 | 12 分 |

### リーグ

自己対戦だけだと「自分だけ強くなったつもり」に陥る。**動かない基準**を必ず混ぜる。

- `random` … 下限の確認（`win_vs_random`）
- `greedy_defense` … 経路が最も長くなる置き方＋弓塔、送りは最小限
- `income_push` … 序盤から送り最優先
- 過去のチェックポイント（最大 8 個）

## 4. バランス調整の回し方

```bash
python sync_balance.py        # ① Java と数値が一致しているか
python balance_analyzer.py    # ② 診断と推奨値
python selfcheck.py           # ③ 環境がルールどおりか
```

**`balance.py` だけを編集する。** Java 側を変えたら `sync_balance.py` が
不一致を検出する（テキスト解析なので、読み取れなかった項目は「一致」ではなく
「読めなかった」として別に報告する — 黙って一致扱いにしない）。

診断は具体的な推奨値まで出すが、**自動適用しない**。適用は GUI の
「バランス」タブのボタンから行い、書き込み時は

1. 宣言型へ強制（整数は整数のまま。`6` を `6.0` にすると `range()` が落ちる）
2. 退避する時点でも型を強制
3. 書いた直後に `ast.parse` ＋再 import で検証し、壊れていたら差し戻す

### 数値を変えたあと、再学習は要るか

| 変更 | 対応 |
|---|---|
| コスト・HP・ダメージ・射程・クールダウン | **学習を継続してよい**（観測が比なので読み替えられる） |
| インカム増加量・収入間隔・カード間隔 | 同上 |
| 塔／送りの**種類を増減** | **再学習**（行動空間の次元が変わる） |
| `MAX_BOARD` / 手札上限 / タワー上限 | **再学習**（観測と行動の形が変わる） |

学習中に `balance.py` が変わった場合は、指紋（`Balance.fingerprint()`）を
毎世代ログに残しているので、指標の変化が学習由来かバランス由来かを後から追える。

## 6. 学習した方策を Minecraft で使う（実装済み）

ロビーの「AI と対戦」「AI 観戦」から、**この学習の成果物がそのまま相手になる**。

```
Minecraft (Java)                          ブリッジ (Python)
  Island / VersusMatch
        │  盤面・塔・敵・財布 = 事実だけ
        ├─ ai/MatchSnapshot ── JSON 1 行 ──▶ mazeward_env/mc_snapshot.py
        │                                        │ 学習と同じ観測を組む
        │                                        ▼
        │                                     policy.Policy（models/ppo_latest.pt）
        └─ ai/AiDirector ◀── 1 手 1 行 ────── mc_brain.py
             │ 合法性は島が判定し、失敗は「無効手」として数える
             ▼
           Island#placeCard / placeTower / upgradeTower / VersusMatch#send
```

### なぜ Java へ移植せず、別プロセスにしたか

当初の設計メモは「重みを JSON で書き出し、観測エンコーダと前向き計算を Java に持つ」
だった。**やめた理由は実装量ではなく、壊れ方の静かさ。**

観測の定義は `observation.py` と `env.py` に 1 本だけある
（14 チャンネル・スカラー 30 個・塔 8 特徴 x 9 種・送り 9 特徴 x 12 種・相手 14 特徴 x 8 席 =
210 次元）。これを Java へ書き写すと、**`balance.py` を触るたびに 2 箇所を直す必要**が生まれる。
片方だけ直しても例外は出ない。行動分布がわずかにずれて、**AI が少し弱くなるだけ**で、
誰も原因に辿り着けない。学習と推論で同じコードを通せば、この事故は起こりようがない。

代償として Python プロセスが 1 つ増えるが、これは自動起動で隠せる
（`BrainClient#ensureBrainProcess`）。**隠せない不整合より、隠せる依存を選んだ。**

副作用として得をしたこと: `models/ppo_latest.pt` を見に行くので、
**学習中のチェックポイントをそのまま遊べる**。世代が進めば次の試合から相手が強くなる。

### 役割分担（ここを混ぜない）

| 誰が | 何を |
|---|---|
| Java | 事実の送信（盤面・経路の折れ線・塔の解決済み性能・敵・財布・送り履歴） |
| Java | **合法性の判定**。方策の手は 1 tick 前の状態を見ているので必ずずれる瞬間がある |
| Python | 観測の組み立て・行動マスク・方策・行動の抽選 |

Java が観測を作らないのと同じ理由で、**Python は合法性を最終判定しない**。
判定は `Island#placeCard` などが持つ 1 本だけにして、失敗は黙って捨て、
「無効手の割合」として次の観測に混ぜる（方策は自分の無駄打ち率を観測に持っている）。

### プロトコル

1 行 1 メッセージ。要求は `req <番号> <JSON>`、応答は `act <番号> <席> <行動>` を
必要なだけ並べて `end <番号>`。番号が合わない応答は捨てる
（遅れて届いた前の局面の手を打たないため）。**1 回の要求に全席ぶんの島を入れる。**
相手の特徴が観測に入っているので、AI が 1 人でも全員の盤面が要る。

行動は方策のヘッドをそのまま文字にしたもの:
`skip` / `card <スロット> <回転> <x> <z>` / `tower <種類> <回転> <x> <z>` /
`upgrade <番号> <特化>` / `sell <番号>` / `send <種類>`。

モデルの操作もこの回線でやる。

| 送る | 返る | 用途 |
|---|---|---|
| `models` | `model <名前>` … `endmodels` | 選べる重みの一覧 |
| `use <名前>` | `hello <ラベル>` / `err …` | 重みだけ差し替える（0.2 秒） |
| `ping` | `hello <ラベル>` | いま何を読んでいるかの確認 |

`use` は **`models/` の中のファイル名だけ**を受け取り、`os.path.basename` で畳んでから開く。
回線越しの文字列をそのままパスにすると、任意のファイルを読ませられる。

差し替えでプロセスを立て直さないのは、torch の読み込みに数秒かかるため。
観測の作りは変わらないので、`load_state_dict` だけで足りる。

### 一致の検査（この方式の生命線）

```bash
cd ai && python mc_parity.py
```

学習環境を回して局面を作り、その内部状態を「Java が送ってくる形」へ書き出してから
`SnapshotEncoder` に通し、`env.observe()` と 1 要素ずつ比べる。
盤面 14 チャンネル・スカラー 210 個・相手 8 席・行動マスク 6 種すべてで
**最大差 0.0**（実測）。ここが通っていれば、残る心配は
「Java が正しいスナップショットを作れているか」だけになり、それは `gradle aiSim` が見る。

### 実測

| 項目 | 値 |
|---|---|
| 往復（2 島 / JSON 5.2KB） | 中央値 6.5ms |
| 往復（8 島 / JSON 20.3KB） | 中央値 10.7ms・最悪 31ms |
| 意思決定の間隔 | 20 tick（学習の 1 ステップと同じ） |

16 倍速・8 島でも 1 秒に 16 回しか要求が出ないので、62ms の余裕に対して中央値 10.7ms。
**倍速でも AI の手数は落ちない。** CPU で回している（GPU は学習に空けておく）。

### 意思決定の間隔を変えないこと

`AiDirector.DECISION_TICKS` は 20（1 秒）。学習環境の `rules.DECISION_TICKS` と同じ。
ここを速くすると学習時より多い手数を持つことになり、
**学んだ配分（守りと送りの比率）がそのまま崩れる**。

### 何が動いているのかを見えるようにする

**「AI が弱い」の原因は 2 通りある**（方策が動いていない / 方策が弱い）。
画面から区別できないと、学習の問題を接続の問題として調べ続けることになる。だから

- サイドバーに常にモデル名を出す（`相手: 学習済み方策 ppo_latest.pt gen20`）
- 頭が切り替わった瞬間にチャットへ流す（起動待ちの数秒は貪欲ボットが打つため）
- チャット `!ai` で接続先・モデル・python プロセスの生死・直近のエラーを全部出す
- 自動起動した python がすぐ死んだ場合（Windows のストア版スタブなど）も理由として残す

### 文字コードの罠（実際に踏んだ）

Minecraft から自動起動すると、子プロセスの標準出力は **親コンソールの符号化**
（日本語 Windows なら cp932）になる。この状態で Python が `—` のような文字を
1 つ出すと `UnicodeEncodeError` で **ブリッジごと落ちる**。落ちた側は
貪欲ボットに切り替わって試合が続くので、**画面には「AI が弱い」としか出ない**。

対策は 3 段構え。1 つでは足りない（どれかが効かない環境がある）。

1. `mc_brain.py` の先頭で `trainer_pb.ensure_utf8_stdout()` を呼ぶ
2. Java 側が子プロセスに `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1` を渡す
3. 起動直後のログは記号を ASCII に留める（1 と 2 が効かない環境の保険）

Java 側も `run` タスクに `-Dstdout.encoding=UTF-8` を入れてある。
入れないと JVM は cp932 で書き、コンソールは 65001 なのでログが全部化ける。
**「起動しました」も「落ちました」も読めない状態では、原因調査が始められない。**

### ブリッジが無いとき

`ai/HeuristicPolicy` へ自動で切り替わる（`bots_heuristic.greedy_defense` と同じ考え方の
貪欲ボット。壁 → 塔 → 強化 → 余ったら送る）。**Python を立て忘れた日に遊べなくなる**
ほうが、相手が弱いことより悪い。試合中にブリッジが復活すれば方策へ戻る。

> 貪欲ボットの順番は「送りを最後」にしてある。送りは常に買えるので先に見ると
> 毎秒それだけを選び続け、25 分でタワー 5 基・送り 1000 回という盤面になった。
> あわせて、ストックが 20 貯まるまで送らない
> （毎秒 1 しか回復しないので、買えるたびに送ると走狗しか撃てない体になる）。

## 7. 次にやること: AI の姿

いまは AI に体が無い。島の上で盤面だけが変わる。

`AiDirector#focusOf(seat)` が「その席が最後に触った場所」を返すようにしてあるので、
次はここに **プレイヤーの見た目のエンティティ** を繋いで、

- 置く対象のセルへ歩いて近づく
- 手に持つものを操作に合わせて持ち替える（壁ブロック / タワーのアイコン / ネザースター）
- 待っているあいだは自分の島を歩き回る

までを足す。**盤面の変化は結果であって、判断そのものは見えない。**
どこへ寄って何を持ったかが見えると、観戦が「盤面の再生」から「相手を読む」へ変わる。
