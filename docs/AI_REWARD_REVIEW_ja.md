## 1. ゲームのルール

Minecraft Java 版サーバー上で動く **迷路構築型タワーディフェンスの対戦モード**。
Emberward の「経路を自分で設計する TD」を対戦に作り替えたもの。

### 盤面

- 各プレイヤーが **自分の島**（21x21 のグリッド、カリキュラムでは 15/17 も使う）を持つ
- 島には **湧き点（spawn）** と **コア（core）** がある。敵は湧き点からコアへ最短経路で歩く
- セルは 5 種: `OPEN`（空き＝カードを置ける）/ `WALL`（障害物＝塔の土台）/
  `ROCK`（初期地形の岩＝最初からある無料の土台）/ `SPAWN` / `CORE`

### 迷路づくり（カード）

- **形状カード**（テトリスのような 2〜6 セルのピース: I2 I3 I4 L J T S Z O U P CORNER DOT）を
  `OPEN` セルに置くと、そのセルが `WALL` になる
- **経路を完全に塞ぐ置き方は禁止**（湧き点からコアへの道が必ず 1 本は残る）
- カードは **30 秒に 1 枚**しか配られない。手札上限 6 枚。**これがこのゲームの主な希少資源**
- 置いた `WALL` が **塔の土台**になる。つまり「迷路を作る」と「塔を置く場所を作る」が同じ行為

### 塔

`WALL` / `ROCK` の上にしか置けない。**塔ごとに必要な土台の形が違う**のが重要。

| 塔 | 土台の形 | コスト | 射程 | クールダウン | ダメージ | 特性 |
|---|---|---|---|---|---|---|
| 弓塔 ARROW | 1x1 | 30 | 5.5 | 12t | 7 | 単体・最前列を狙う |
| 氷塔 FROST | 1x1 | 45 | 5.0 | 18t | 3 | 減速 40% / 45t |
| 送還塔 BANISHER | 1x1 | 75 | 5.5 | 1200t | 5 | 敵 1 体を湧き点へ戻す |
| 火炉 BRAZIER | 1x2 | 60 | 3.6 | 20t | 0 | 範囲燃焼 5dps / 60t |
| 呪詛塔 HEXER | 1x2 | 95 | 6.0 | 30t | 0 | 被ダメ +35% を付与 |
| 弩塔 BALLISTA | **1x3** | 100 | **12.0** | 50t | 30 | 貫通 3 体・最後尾を狙う |
| 砲塔 CANNON | **2x2** | 110 | 6.5 | 40t | 26 | splash 2.2・最硬を狙う |
| 雷塔 TESLA | **2x2** | 130 | 5.0 | 22t | 11 | 連鎖 3 体・最密を狙う |
| 監視塔 WATCHTOWER | **2x2** | 120 | 5.0 | — | 0 | 周囲の塔に +30% ダメージ / +15% 連射 |

- 強化は Lv3 まで。Lv3 で 2 択の特化を選ぶ（例: 弓塔 = 狙撃 / 連射）
- **1 島あたり塔は 24 基まで**
- 売却は投資額の 60% が戻る

**設計意図**: 2x2 や 1x3 の塔は強いが、**そのための土台を意図して作る必要がある**。
「どの形のカードをどう並べれば 2x2 の台ができるか」を考えるのがこのゲームの肝。

### 経済と対戦

- 開始: コイン 100 / インカム 5 / ライフ 20 / ストック 30
- **インカム** = 一定間隔（2 人戦なら 5 秒、8 人なら 10 秒）ごとに配られるコイン。恒久的に増える
- **送り（send）**: コインを払って **生存している全員の島に同時にモンスターを送る**（相手は選べない）
  - 送ると **インカムが恒久的に増える**（走狗 15 コイン → +1、庇護者 150 コイン → +4）
  - 高コストの送りは **インカム下限で解禁**される（走狗 0 / 石背 40 / 庇護者 230 / 災厄 350）
  - ストックを消費し、1 秒に 1 回復（上限 30）＝ 送りの連打を止める
- **開始 60 秒は送れない**（準備時間）
- 送られたモンスターがコアに触れると **受け手のライフが 1 減り、送り主のライフが 1 戻る**
  （送り主の上限は超えない ＝ 削られたぶんを攻めで取り返す動きだけが報われる）
- 送られたモンスターを倒すと **防御側にコイン**（送りコストの 20%）と少量のインカムが入る
- 15 分でサドンデス（リークダメージ 2 倍）
- ライフ 0 で脱落。最後の 1 人が勝ち。2〜8 人の FFA

### 敵

徘徊者・疾走者・重装兵・浮遊体（**飛行 = 迷路を無視して直線で飛ぶ**）・祈祷師（回復オーラ）・
妨害者（塔を黙らせる）・瞬移体（被弾時にワープ）・庇護者（被ダメ軽減オーラ）・分裂体・
熱塊（燃焼無効）・終焉騎（**倒しても 1 度復活し、受け手のライフ上限を 1 奪う**）・災厄（ボス。周回する）

## 2. 何を作っているか

- **ヘッドレスのゲームシミュレータ**を Python + numpy で自作（Minecraft を起動せずに回す）。
  Java 実装の移植で、数値は 1 つのファイルに集約してある
- そこで **PPO の自己対戦**で方策を学習
- 学習した方策は **TCP のブリッジ経由で実際の Minecraft サーバーの AI として動く**。
  観測を組む実装は学習側と共通（1 本しかない）。観測の一致は自動テストで検証済み
- 規模: 128 環境並列、1 世代 = ゲーム内 30〜60 分ぶん。**37 世代 = ゲーム内 7 時間**回した時点

### 学習の設定

| 項目 | 値 |
|---|---|
| アルゴリズム | PPO（clip 0.2, epochs 3, minibatch 1024） |
| lr | 2.5e-4 |
| γ / GAE λ | **0.997** / 0.95 |
| エントロピー係数 | 0.02 |
| 1 意思決定 | **ゲーム内 20 tick = 1 秒**（1 試合 12 分 = 720 ステップ） |
| 対戦相手 | 自己対戦 + 過去チェックポイントのリーグ + 基準ボット 35% |
| カリキュラム | 15x15/2人/4分 → 17x17/2人/6分 → 21x21/2-4人/8分 → 21x21/2-8人/12分 |
| ネットワーク | 盤面 CNN + スカラー MLP + 相手エンコーダ → 共有胴体、ヘッドのみ分岐。33 万パラメータ |
| 価値関数 | **1 つ**（迷路・塔・送りが同じコインを奪い合うので、配分を 1 つの価値で比較させたい） |

`地上の経路` / `飛行の直線ルート` / `敵の数` / `敵の HP 比` / `コアへの近さで重み付けた脅威`

### 4-2. スカラー 210 次元

経済（コイン・インカム・ストックを「何秒ぶんか」の比で）、時間、手札、順位、
送りの履歴、塔の本数と平均レベル、など。**絶対値ではなく比で渡す**方針
（バランス数値を変えても壊れないようにするため。ドメインランダム化と対で使う）。

### 4-3. ★論点: 塔 1 種につき 8 特徴

```python
feats = [
    dps0 / cost,              # ← DPS / コスト
    dps3 / full_cost,         # ← 完成時の DPS / 総コスト
    range / board_size,
    cost / income,            # 何秒ぶんのインカムで買えるか
    full_cost / income,
    splash / 4,
    chain / 8,
    slow + burn / 20,
]
```

**`dps = damage * 20 / cooldown` で、splash・chain・slow・burn・支援効果を含んでいない。**
その結果、観測上は次のように見えている。

| 塔 | 観測が伝える DPS/コスト |
|---|---|
| ARROW | **0.389**（1位） |
| BALLISTA | **0.360**（2位。しかも貫通 3 体を無視した値） |
| TESLA | 0.231（連鎖 3 体を無視） |
| CANNON | 0.118（splash を無視） |
| HEXER / WATCHTOWER | **0.000** |

### 4-4. 相手

実ゲームで **本当に見える情報**（迷路の形・塔の配置・強化状態）は全部渡す。
コイン・インカム・ストック・手札は見えないので **送りの履歴からの推定値**だけ。
最大 8 人ぶんの固定スロット + マスクで、人数が変わっても形が変わらないようにしている。

## 5. 報酬

### 5-1. 旧報酬（壊れていた）

```python
WIN/LOSE            = ±1.0     # 終端。FFA は順位報酬
COIN_GAIN           = +0.001   # 毎ステップの獲得コイン
LIFE_LOST           = -0.5     # ライフ 1 につき
LIFE_REGAINED       = +0.5     # 送りが通って自分のライフが戻ったぶん
MAX_LIFE_STOLEN     = -0.5
COVERAGE_GAIN       = +0.01    # 射程カバレッジ重み付き経路長の「増分」
IDLE_PENALTY        = -0.01    # 射程内に敵が来なかった塔の割合
HAND_FULL_PENALTY   = -0.005
INVALID_ACTION      = -0.002
```

設計意図としては「整形は合計で主軸の 10% 以下」。**実測は全然そうなっていなかった。**

学習済み方策（第 37 世代）を回して 15 分 1 試合ぶんの各項を積算した結果:

| 項 | 1 試合の合計 |
|---|---|
| **`COIN_GAIN`** | **+29.6** |
| **`IDLE_PENALTY`** | **-8.7** |
| `COVERAGE_GAIN`（核心のはずだった項） | **+0.037** |
| ライフ増減 | 0.000 |
| 合計 | **+20.9** |
| （参考）勝敗 | ±1.0 |

**整形が主軸の 30 倍**。この AI は勝敗ではなく **コイン総獲得量**を最大化していた。

#### なぜこうなったか

1. **`COIN_GAIN` が青天井。** 2 人戦の収入間隔は 5 秒で、送りの `income_gain` が
   雪だるま式に効く。1 試合の総獲得コインが 3 万に達し、0.001 x 30000 = +30
2. **`COVERAGE_GAIN` は差分（望遠鏡和）なので総和が「最終値 − 初期値」で頭打ち。**
   どんなに良い迷路を作っても 1 試合で +0.05 が上限。コイン項の 1/800 で、事実上死んでいた
3. **`IDLE_PENALTY` は「自島に敵がいない時間」への定額税だった。**
   敵が 1 体もいなければ全塔が遊休判定になるので、相手が攻めてこない試合では
   自分では避けられない -0.01/step のドリフトになる
4. **送りには即時報酬が実質ゼロ。** 相手のライフを削っても送り手には何も入らない
   （`LIFE_LOST` は削られた側にしか入らない）。`LIFE_REGAINED` は
   「自分が失ったライフの取り戻し」なので、**ライフ満タンの間は送りが通っても 0**。
   実測でも 1 試合の送り由来の直接報酬は **0.000** だった

#### 観測された症状（Minecraft 上でも再現）

| 症状 | 実測 |
|---|---|
| **弓塔しか建てない** | 設置内訳 `ARROW 231 / BALLISTA 105 / CANNON 4 / WATCHTOWER 5 / TESLA 1`。**DPS/コストの 1 位・2 位そのまま** |
| **送りが遅い** | 塔が 24 基の上限に達してコインが余ってから送り始める |
| **2x2 の土台を意図して作らない** | 2x2 の台は盤上に 60〜90% の時間で存在するのに、2x2 塔の設置は全体の 2.9%。コインが苦しい条件では **500 基中 0 基** |
| **相手が送ってこないと何も起きない** | 撃破報酬が入らないとコインが 10〜20 で張り付き、20 分回しても塔が 5 基前後で停滞（Minecraft で人間と対戦したときにこれが出た） |

#### 学習ログの傾向（第 1〜37 世代）

- **エントロピーが 0.24 → 2.8 と上がり続けている**（収束ではなく発散側）
- **KL が 0.001〜0.005** ＝ 更新がほとんど方策を動かせていない
- 第 36 世代で value_loss が 0.5 → 8.3 → 11.3 に爆発（リターンの規模が ±30 なので当然）
- 累積ゲーム内時間 7 時間

### 5-2. 新報酬（今回入れたもの）

**方針: 主軸は勝敗のみ。整形は「盤面の良さ」のポテンシャル差分だけにして、総量を有界にする。**

「足し続けられる量」をそのまま報酬にすると必ず主軸を追い越す。
削り合い・送り合いが成立するこのゲームでは、両者が交互に殴るだけで無限に稼げてしまう。
そこで整形をポテンシャル差分に限定した (Ng, Harada &amp; Russell 1999):

```
整形報酬 = γ Φ(s') − Φ(s)
```

エピソード全体で足すと **Φ の最終値と初期値の差**にしかならない（望遠鏡和）。
密な信号は途中で受け取れるのに、**総量は Φ の幅を超えられない**。

Φ は **すべて相手との差**で作る（自分の絶対値にすると「両者が一緒に太る」で稼げてしまう）:

```python
Φ = 0.60 * clip(自分のライフ率 − 生存相手の平均ライフ率, -1, 1)
  + 0.20 * clip((自分のインカム − 相手平均インカム) / (自分 + 相手 + 20), -1, 1)
  + 0.15 * clip(射程カバレッジ重み付き経路長 / (盤面の一辺 * 15), 0, 1)
```

| 項 | 意図 |
|---|---|
| `life` | **相手から奪えば +、削られれば −**。取り返しても Φ が元に戻るだけで往復の合計は 0 ＝ 無限ファーム不可 |
| `income` | 送りでインカムを伸ばす行動がここで報われる。両者が同じだけ伸ばしたら 0 ＝ 雪だるま不可 |
| `maze` | 迷路の形。頭打ちがあるので「無駄に長い迷路」を伸ばし続けても途中で止まる |

直接の罰として残したのは、ポテンシャルにできない片側だけのもの:

```python
HAND_FULL_PENALTY = -0.005   # 手札上限で溢れさせている
INVALID_ACTION    = -0.002   # 空振り
MAX_LIFE_STOLEN   = -0.05    # 終焉騎に上限を奪われた（取り返せない）
```

**`IDLE_PENALTY` は廃止。** 24 基に対して敵が数体しかいない普通の局面でも遊休率は
0.8 を超える。「塔の置き方」ではなく「塔を建てたこと」への課税になっていた。
経路から外れた塔を咎める役目は Φ の `maze` 項が果たす
（経路を覆わない塔は weighted_path を 1 も増やさないので、罰がなくても得しない）。
遊休率は報酬から外して**指標としてだけ残した**。

#### 実測（同じ第 37 世代の方策で測り直し）

| 項 | 旧 | 新 |
|---|---|---|
| コイン / インカム | +29.6 | Φ に統合 |
| 遊休 | -8.7 | 廃止 |
| カバレッジ | +0.037 | Φ に統合 |
| **整形の合計** | **+20.9（主軸の 2090%）** | **-0.19（主軸の 19%）** |

## 6. まだ解けていない論点（ここに意見がほしい）

### ① 観測の「DPS / コスト」をどうするか（§4-3）

いまの実装は **報酬が「コインを稼げ」と言い、観測が「弓が一番効率がいい」と教えている**状態だった。
報酬側は直したが、観測側はまだそのまま。選択肢:

- **(a) 消す。** 塔の生の性能（射程・クールダウン・ダメージ・splash・chain・slow・burn）と
  コストを別々に渡して、価値の合成はネットワークに任せる
- **(b) 直す。** splash・chain・slow・burn・支援を含んだ「実効価値 / コスト」に置き換える。
  ただし「実効価値」の定義自体が設計者のバイアスになる
- **(c) 残す。** バランス数値を変えても再学習なしで動く、という当初の狙いのために

**どれが良いか。** なお **(a)(b) どちらも観測の次元が変わるので、既存のチェックポイント
4 本がすべて読めなくなる**（報酬を作り直した以上ゼロから回し直す前提ではある）。

### ② 「2x2 の土台を意図して作る」をどう学ばせるか

これがゲームの肝なのに、いまの AI は完全に見落としている。

- 報酬で誘導する？（例: 高コスト塔を建てたら Φ が上がる項）→ 設計者の答えを押し付けることになる
- 観測を足す？（例: 「あと 1 枚置けば 2x2 の台ができるセル」のチャンネル）→ ヒントとしては強力だが、これも押し付け
- それとも **弓スパムが実際に強いだけ**で、AI は正しい？
  （24 基上限で DPS/コスト 1 位を並べるのは合理的とも言える。だとすればゲームバランス側の問題）

**バランスの問題なのか、学習の問題なのか**を切り分ける良い方法があれば知りたい。

### ③ γ = 0.997 と試合長

1 試合 720〜1800 ステップ。γ=0.997 の実効視野は約 333 ステップなので、
**開幕の 1 手から見た勝敗は 0.997^720 ≈ 0.11 まで減衰する**。
リターン正規化・γ を上げる・試合を短くする・価値関数を 2 本（勝敗用と整形用）に分ける、
どれが筋が良いか。

### ④ エントロピーが上がり続ける

係数 0.02 で、0.24 → 2.8。KL は 0.001〜0.005。
「勝敗の勾配が弱すぎてエントロピー項に押し負けている」と読んでいるが、
新報酬で解決するのか、係数を下げる / 減衰させるべきか。

### ⑤ 自己対戦の相手構成

いまは 自己対戦 + 過去チェックポイント + 基準ボット 35%（守り一辺倒 / 送り一辺倒 / ランダム）。
**旧報酬下では「相手が送ってくれる撃破報酬」に経済が依存していた**ので、
攻めない相手には何もできない方策になっていた。
新報酬でこれは解消するはずだが、相手の多様性の担保として他に入れるべきものはあるか。

### ⑥ その他、もっと良い整形報酬はないか

いま Φ に入れていないが候補になりそうなもの:

- 塔の**実効 DPS 総和**（射程内に敵が来る前提での期待ダメージ）
- **経路に沿った累積被ダメージ**（湧き点からコアまで歩いたとき何ダメージ受けるか）
  ＝「その迷路と塔の組み合わせがどれだけ強いか」の直接的な指標
- 相手の島に送ったモンスターの**踏破率**（どこまで進めたか）
- 手札とコインの**遊休資源量**

## 7. レビューを受けて入れた変更（2026-09-02）

Gemini / Qwen / ChatGPT / Kimi の 4 つに §6 を投げた回答をもとに、採否を決めた記録。

### 採用したもの

| # | 指摘 | 対応 |
|---|---|---|
| 1 | 観測の `DPS/コスト` は消すべき（4 つとも (a) を推奨） | **削除。** 塔の特徴を 8 → 19 に作り直し、生の性能だけを渡す |
| 2 | 生存者だけで相手平均を取ると、第三者の脱落が罰になる（Qwen） | **修正。** 脱落者もライフ 0 / インカム 0 として分母に残す |
| 3 | γ<1 では単純和が端点の差にならない（ChatGPT） | **文言を修正し、検算を自動テストに追加。** 割引和は端点で決まる（実測誤差 1e-6 未満）が、ログに出る単純和には (1−γ)ΣΦ ぶんの漏れがある |
| 4 | `maze` 項だけ絶対値で「相手との差」になっていない（Qwen / ChatGPT） | **相対化。** ついでに中身を §6-⑥ の累積被ダメージへ置き換えた |
| 5 | `HAND_FULL_PENALTY` はポテンシャルではないので上限が無い（ChatGPT） | -0.005 → **-0.002** |

#### 1 の詳細: 観測から消したもの・足したもの

削除: `DPS/コスト`、`完成時DPS/総コスト`。

**消してみて分かったこと**: 旧観測には `slow + burn/20` を 1 つに畳んだ枠しかなく、
**呪詛（vulnerability）・支援（boost）・送還（banish）は 1 つも入っていなかった**。
つまり呪詛塔・監視塔・送還塔は、観測上「射程とコストしか無い塔」で、
DPS/コストも 0.000。AI が建てないのは当然だった。

新しい 19 特徴（塔 1 種あたり）:

```
コスト/100, コスト/インカム, Lv3総投資/400,
Lv0ダメージ, Lv3ダメージ, Lv0発射レート, Lv3発射レート, Lv0射程, Lv3射程,
splash, chain, slow, burn, vulnerability, boost_damage, boost_rate, banish,
土台のセル数, 土台の長辺
```

最後の 2 つは「この塔は 2x2 を要求する」というルールそのもの。
設置マスクは「いま置けるか」しか伝えないので、形は別に渡す。
`DOT(1,1) / I2(2,2) / I3(3,3) / O(4,2)` で 4 種類を一意に区別できる。

`SCALAR_DIM` が 210 → 309 に変わったので、**既存のチェックポイント 4 本は読めない**。
リーグ側は元から握り潰す作りだったのでそのまま、ブリッジ側は
「形が合いません、学習をやり直してください」と出して貪欲ボットに落ちるようにした。

#### 4 の詳細: `maze` → `threat`（経路踏破時の累積被ダメージ）

基準の敵が湧き点からコアまで歩いたとき、合計で何ダメージ受けるか。
**セル数ではなく滞在時間で積分する**のが要点。

```
そのセルの滞在時間 = 1 / (敵の速度 × (1 − slow))
そのセルの被ダメ   = 滞在時間 × (覆っている全塔のDPS合計) × (1 + vulnerability)
```

積み上げ規則は戦闘実装に合わせた（slow も vulnerability も加算ではなく最大値。
監視塔のバフは塔の `_st_damage` / `_st_cooldown` に合成済み）。

蛇行経路に弓 8 基を置いた盤面で、**9 基目の 1 コインあたりの限界価値**:

| 9基目 | コスト | 新指標 | 旧指標（カバレッジ） |
|---|---|---|---|
| **氷塔** | 45 | **17.10（1位）** | 0.556（3位） |
| 弓塔 | 30 | 9.55 | **0.900（1位）** |
| 弩塔 | 100 | 7.42 | 0.680 |
| **呪詛塔** | 95 | **4.34** | 0.347 |
| **監視塔** | 120 | **4.21** | 0.208 |
| 砲塔 | 110 | 4.19 | 0.355 |
| 雷塔 | 130 | 1.75 | 0.192 |
| 火炉 | 60 | 0.53 | 0.117 |

**氷塔が 1 位になる。** 自分は 3 ダメージしか出さないのに、周りの弓 8 基の
攻撃回数を 1.67 倍にするから。旧指標の順位は、実際に建っていた順番
（弓と弩だけ）とそのまま一致していた。

**誰がいくら出したかは分解しない。** 監視塔の限界価値 +505 は 1 点も監視塔が
出していないが、ポテンシャル差分 `Φ(置いた後) − Φ(置く前)` は自動的にこの値になる。
塔ごとに帰属させると監視塔・呪詛塔・氷塔の取り分は 0 になってしまう。

近似していること: splash と chain は「同時に何体いるか」に依存するので含めていない
（雷塔が低く出るのはこのため）。燃焼は射程内にいるあいだのぶんだけ。
飛行敵は迷路を無視するのでこの指標に入らない。送還塔も表現できていない。

### 現在の Φ

```python
Φ = 0.60 * clip(自分のライフ率 − 相手平均ライフ率, -1, 1)
  + 0.15 * lead(インカム,   相手平均, floor=20)
  + 0.20 * lead(累積被ダメ, 相手平均, floor=300)

lead(a, b, f) = clip((a − b) / (a + b + f), -1, 1)   # 両者が一緒に太ったら 0
```

実測（守り一辺倒ボット vs 送り一辺倒ボット、15 分）: 途中報酬の合計 **+0.13**、
Φ の範囲 -0.12〜0.75、割引和と端点の差は一致（誤差 1e-6 未満）。
2 人戦では Φ が両者で完全に反対称（+0.119 / −0.119）になることも確認した。

### 採用しなかったもの

| 指摘 | 判断 |
|---|---|
| **階層行動のエントロピー計算が間違っているのでは**（Qwen） | **外れ。** [policy.py](../ai/policy.py) の `evaluate` はサブヘッドを行動種別でゲートしている。使わなかったヘッドは log 確率にも entropy にも入らない |
| **ライフ率の分母が「現在の最大ライフ」だと上限剥奪が見えない**（Qwen） | **元から開始ライフ基準**なので問題なし |
| **γ を上げろ / 下げろ** | **保留。** Gemini・Qwen は 0.999〜0.9995 へ上げろ、Kimi は 0.99 へ下げろ、ChatGPT は据え置き、と割れた。報酬のスケールが 30 倍変わった直後なので、まず新報酬で回してから測る |
| **終端報酬を ±3〜5 に増やせ**（Qwen） | **不要。** Φ は ±0.95 で有界、実測の途中報酬は主軸の 13%。スケールを動かすと価値関数の学習し直しになる |
| **終端で Φ=0 にせよ**（Qwen・ChatGPT） | **一部だけ採用。** 脱落した島は `live=0` で Φ が 0 になるので、脱落については既にそうなっている。時間切れの引き分けだけ Φ が残るが、γ^T Φ_T ≈ 0.08 で有界かつ結果と同じ向き |
| **高コスト塔・2x2 建設にボーナス** | **入れない**（4 つとも同意見） |

### 次にやるべきこと

観測と報酬の両方が変わったので、**ゼロから学習し直す**。そのうえで:

1. **2x2 を使うヒューリスティックボットを作り、弓スパムボットと戦わせる。**
   3 つが揃って挙げていた切り分け方で、これが一番早い。
   2x2 ボットが勝てないなら**ゲームバランスの問題**、勝てるのに AI が使わないなら
   **学習・探索の問題**、と分かれる
2. ヘッドごとのエントロピーを `entropy / log(選べる手の数)` で記録する。
   いまの合計値 2.8 は `cell` ヘッド（729 択、上限 6.59）に引きずられている可能性がある
3. 塔の種別内訳・2x2 設置率をダッシュボードの指標に入れる

## 8. 塔構成ベンチの結果（2026-09-02）— バランスか学習かの切り分け

§7 の「次にやるべきこと 1」を実施した。実装は
[ai/tower_bench.py](../ai/tower_bench.py) と
[bots_heuristic.py](../ai/mazeward_env/bots_heuristic.py) の構成ボット群。

### 測り方

対戦形式でやると**決着が最初の 4 分でつき、そのあと 16 分は双方 1 体も
漏らさない膠着**になって、塔の構成の差が埋もれた（実測）。
そこで経済の交絡を消した防衛試験にした。

- 送りを封じ、**インカムを全員同じ固定値**にする（＝同じ金）
- 一定間隔で**同じ構成の波**を全員の島に湧かせる（12 分で 720 体、後半ほど重い）
- ライフを 10000 にして死なせない。**漏らした回数だけ**を数える
- 迷路の作り方・強化・送りの手順は全ボット共通。違うのは塔の選び方と
  「カードで 2x2 の土台を作りにいくか」だけ

### 結果（インカム 80 固定 / 12 分 / 6 島平均 / 720 体）

| ボット | 漏れ率 | 塔 | 経路 | 累積被ダメ | 構成 |
|---|---|---|---|---|---|
| **big_tower** | **15.1%** | 24 | 48.6 | 69,511 | ARROW69% BALLISTA13% CANNON8% TESLA6% |
| pierce_mix | 28.5% | 24 | 66.3 | 47,518 | ARROW90% BALLISTA10% |
| arrow_spam | 29.4% | 24 | 66.8 | 44,580 | ARROW100% |
| support_mix | 31.7% | 24 | 64.5 | 149,557 | ARROW58% FROST34% HEXER8% |
| splash_mix | 39.0% | **15.5** | 45.1 | 13,593 | CANNON52% TESLA48% |
| arrow_pads | **50.6%** | 24 | 40.4 | 32,944 | ARROW100% |

インカム 30（金欠）でも順位は同じ（big_tower 20.6% / arrow_spam 40.5%）。

### 読み取れること

#### ① 弓スパムは最適解ではない → **学習側の問題**

`big_tower` は `arrow_spam` の**半分しか漏らさない**。金欠でも潤沢でも同じ。
しかも純粋な 2x2 構成ですらなく、土台が足りずに**弓が 69% 混ざった状態**でこれ。
**ゲームバランスの問題ではなく、学習・観測・報酬の問題**と確定した。

#### ② 「2x2 全振り」も間違い → 混ぜるのが正解

`splash_mix`（砲塔と雷塔だけ、弓に一切逃げない）は 24 枠中 **15.5 基**しか
建てられず、漏れ率も 39.0% と悪い。土台の制約が厳しすぎる。
**弓を主体に大型塔を混ぜる**のが正解で、これは AI が発見しにくい形をしている。

#### ③ ★ これは「2 手先まで進まないと損をする」改善だった

いちばん重要な発見。**迷路の作り方だけ**を変えた対照群（`arrow_pads`）を見る。

| | 迷路 | 塔 | 漏れ率 |
|---|---|---|---|
| arrow_spam | 経路を伸ばす（66.8） | 弓のみ | 29.4% |
| **arrow_pads** | **2x2 の土台を作る（40.4）** | 弓のみ | **50.6%** ← 悪化 |
| **big_tower** | 2x2 の土台を作る（48.6） | 混合 | **15.1%** ← 最良 |

- 迷路だけ 2x2 狙いに変えると経路が 66.8 → 40.4 と短くなり、**漏れがほぼ倍に悪化する**
- 塔だけ変えたくても、土台が無いので大型塔は置けない（`splash_mix` が 15.5 基で止まる）
- **両方を同時に変えて初めて 15.1% になる**

同じ迷路で塔だけ比べると 50.6% → 15.1% で、**塔の構成の効果は 3.4 倍**。
つまり効果自体は巨大なのに、**片方だけ動かすとどちらも損をする**。
PPO が 37 世代かけて見つけられなかったのは当然で、
これは報酬のスケールの問題ではなく**探索の谷**の問題。

観測に「あと 1 枚で 2x2 の土台ができるセル」を入れる案は、
設計者の答えの押し付けというより**この谷を渡す橋**として意味がある。

#### ④ ★ Φ の `threat` 項は FROST を過大評価している（要修正）

§7 で入れた「経路踏破時の累積被ダメージ」を実際の防御力と突き合わせると、
おおむね順位は合っているが **`support_mix` だけ大きく外れる**。

| | 累積被ダメ | 実際の漏れ率 |
|---|---|---|
| support_mix | **149,557（最大）** | **31.7%（下から 2 番目）** |
| big_tower | 69,511 | 15.1%（最良） |

原因は指標が**敵 1 体が単独で歩く前提**になっていること。

- 氷塔 Lv3 の減速は上限 0.75 なので滞在時間が 4 倍になり、指標も 4 倍に膨らむ。
  だが**射程内で敵が死ぬなら、伸びた時間は無駄**（オーバーキルを打ち切っていない）
- 実戦では敵が同時に何体も来るので、塔の DPS は的の間で**分割される**。
  減速は敵を溜めるので、むしろ分割を悪化させうる
- 逆に splash と chain は「同時に何体いるか」に効くのに、指標に入っていない
  （雷塔・砲塔が過小評価される）

**omission は 2 つに見えて根は 1 つ**で、「単体で歩く敵」を測っているのに
実際は**スループット律速**という点。修正案:

1. splash / chain を「想定クラスタ体数」で期待ヒット数として掛ける
2. 減速の寄与に上限をつける（滞在時間の倍率を頭打ちにする）
3. あるいは基準敵の HP を実際に削るシミュレーションにして、
   **オーバーキルを打ち切る**（＝ 1 回の踏破で何体倒せるかを数える）

- `arrow_spam` / `big_tower` / `splash_mix` をリーグの基準ボットに入れる

## 9. §8 の測り直しと、Φ・観測の作り直し（2026-09-02 その2）

### 9-1. ★ §8 の数字には測定アーティファクトがあった

§8 は **5 秒に 4 体**の波で測っていたが、1 島の同時敵数には
**48 体の上限**がある (`balance.MAX_ENEMIES`)。実測すると
**依頼した湧きの 40.7% が捨てられていた**。捨てられた敵は漏れないので、
`漏れ数 / 依頼数` は守りを実際より強く見せる。

取りこぼしは全ボットでほぼ同じ（arrow_spam 704 / arrow_pads 705）だったので
**順位そのものは保たれる**が、**差の大きさは信用できない**。
流量を上限未満（5 秒に 2 体）に落とし、シードを 2 本に増やして測り直した。

### 9-2. 測り直した結果（インカム 80 / 12 分 / 8 島 x 2 シード / 288 体）

| ボット | seed 0 | seed 7 | 平均 | 経路 | 構成 |
|---|---|---|---|---|---|
| **big_tower** | 53.8% | 44.9% | **49.4%** | 44.1 | ARROW65% BALLISTA15% CANNON11% TESLA8% |
| support_mix | 49.0% | 66.8% | 57.9% | 58.4 | ARROW58% FROST34% HEXER8% |
| pierce_mix | 54.8% | 71.7% | 63.3% | 57.1 | ARROW92% BALLISTA8% |
| splash_mix | 69.9% | 59.3% | 64.6% | 42.4 | CANNON52% TESLA48% |
| arrow_spam | 57.5% | 73.3% | 65.4% | 56.5 | ARROW100% |
| **arrow_pads** | 91.8% | 91.0% | **91.4%** | 36.4 | ARROW100% |

**§8 の結論のうち、残るものと訂正するもの:**

| §8 の主張 | 測り直し後 |
|---|---|
| 弓スパムは最適解ではない → 学習側の問題 | **残る。** big_tower が両シードとも arrow_spam より良い（49.4% vs 65.4%） |
| その差は「半分」 | **訂正。** 15.1% vs 29.4% は上限による過小評価。実際は **49.4% vs 65.4% で 16 ポイント差** |
| 2 手同時に動かさないと損をする（探索の谷） | **残る。むしろ強まった。** arrow_pads は両シードとも 91% で断然最悪 |
| 「2x2 全振り」も間違い | **残る。** splash_mix は 24 枠中 15.5 基しか建たず 64.6% |

シード間のばらつきが大きい（support_mix は 49% と 67%）ので、
**中位 4 種の細かい順位は 2 シードでは決められない**。
確かなのは「big_tower がいちばん良い」と「arrow_pads が断然悪い」の 2 点だけ。

### 9-3. Φ の `threat` 項を作り直した

**直したこと。** 敵 1 体が単独で歩く前提をやめ、**流れてくる敵の 1 体**を測る。
敵が λ 体/秒で流れると、ある塔の射程内には λ x (射程内の滞在時間) 体がいるので、
1 体が受けるダメージはそのぶん割られる::

    減速で滞在時間が 2 倍 → 同時に射程内にいる敵も 2 倍 → 相殺

減速が効くのは**塔が暇なとき**だけ、splash と chain は**飽和しているときにこそ**効く。
`share = min(1, 同時に叩ける体数 / 同時に射程内にいる体数)` でこれを表した。

**効果。** 氷塔の過大評価が消えた。

| | 旧 threat | 新 threat | 実際の漏れ率 |
|---|---|---|---|
| support_mix（氷塔 34%） | **149,557（最大）** | 17,000 台 | 57.9%（中位） |
| big_tower | 69,511 | **24,000 台（最大）** | 49.4%（最良） |

**残る限界。** 塔が同じで**迷路だけ**違う 2 つの盤面を区別できない
（弓 24 基 Lv3 で経路 60.2 と 35.6 → どちらも 13,100 台。
実際の漏れ率は 57.5% と 91.8%）。飽和した盤面では「同時に狙われる敵の数」が
経路長に比例して増えるので、1 体あたりで見ると経路長が式から落ちる。
実戦ではそう綺麗に分配されない（弓は FIRST 狙いなので同じ敵に集中して過剰殺傷する）。

そこで Φ に**経路の露出**を別項として戻した。現在の Φ::

    Φ = 0.60 * clip(ライフ率の差, -1, 1)
      + 0.15 * lead(インカム,   相手平均, floor=20)
      + 0.15 * lead(累積被ダメ, 相手平均, floor=300)
      + 0.10 * lead(経路露出,   相手平均, floor=200)

`LOAD_RATE`（想定する敵の流量）は 0.2 体/秒。**大きすぎると盤面の形が消える**
（0.5 にしたら経路 66.8 と 40.4 の盤面が完全に同じ値になった）。

### 9-4. 2x2 の affordance を観測に入れた

盤面チャンネルを 14 → 16 に。実装は `grid.big_pad_masks`（学習側とブリッジで共通）。

- `CH_PAD_NOW` … いま大型塔（2x2 / 1x3）を載せられる土台
- `CH_PAD_GAIN` … **あと 1 マス置けば**大型塔の土台になる、カードを置けるセル

塔の設置マスクは「いま置けるか」しか伝えないので、後者はここでしか読めない。
§8 ③ の谷（迷路だけ変えると 91%、塔だけ変えると土台不足で 15 基）を渡る橋として入れた。

## 10. 指標の作り直し（2026-09-02 その3）— 「積み上げてバランスを判断する」ための準備

「いっぱい回したら積み上がるデータでバランスを判断したい」という要件に対して、
**いまの収集内容では足りなかった**ので作り直した。

### 10-1. 何が足りなかったか

| 穴 | なぜ致命的か |
|---|---|
| **勝った側と負けた側が混ざっていた** | 1 試合の指標が全部 `[seats].mean()` だった。`tower_type_rates` も `income` も `leaks` も勝者と敗者の平均で、**「どの構成が勝つのか」を後から一切問えない**。§8 のベンチを丸ごと作る羽目になったのは、まさにこの質問に答えられなかったから |
| **漏れの分母が無かった** | `leaks_per_game` は回数だけ。「何体来たか」が無いと、守りが強いのか攻めが軽かったのか分からない。しかも敵の同時上限が湧きを黙って捨てるので、実測では 4 割が消えていた |
| **送りの突破率が無かった** | `leak_type_rates` は「漏れのうち何割がこの種類か」で、**安くて何度も送る敵が自動的に上位に来るだけ**。見たいのは「その種類を送ったら何割が通るか」 |
| **塔ごとの実績が無かった** | 構成比しか残らない。**監視塔と呪詛塔は自分では 1 ダメージも出さないので、構成比では永久に評価できない** |
| **平均しか残らない** | 大勝ちと大負けを繰り返す戦略と、いつも引き分ける戦略が同じに見える |
| **方策と一緒に動く** | 学習ログの指標は方策が変わるから動く。バランスが変わったのか方策が変わったのかを切り分けられない |

### 10-2. 入れたもの

**① 席ごとの内訳 → 勝者 / 敗者で分けて集計**

`info["per_seat"]` に席ごとの成績を出し、`winner_*` / `loser_*` に集計する。
第 1 世代（未学習）でいきなりこう出た::

    winner_towers 3.56   loser_towers 0.00
    winner_leak_rate 0.083   loser_leak_rate 0.837
    winner_tower_mix {ARROW: 0.97, BALLISTA: 0.03}   loser_tower_mix {}

「勝った側は塔を建て、負けた側は 1 基も建てなかった」。
従来の `tower_count_final: 6.08`（両者の平均）からは読めない。

**② 漏れ率と、上限で捨てた湧き**

席ごとに `received` / `spawn_dropped` / `leak_rate`。
捨てた湧きを数えるようにしたので、§9-1 の歪みはもう不可視にならない。

**③ 送りの種類ごとの突破率** (`breakthrough_rates`)

「その種類を送ったら何割が通るか」。実測例: `WHELP 11.3% / SAPPER 72.7%`。

**④ ★ 塔の種類ごとの与ダメージ功績** (`damage_share_by_kind` / `damage_per_tower_by_kind`)

バランス判断の本命。1 発の被ダメージを

    素の火力 x 支援倍率 x 呪詛倍率

に分解し、**増えたぶんを供給元の塔へ返す**。交差項はどちらの手柄とも言えないので
半分ずつ配る（2 人ゲームの Shapley 値と同じ配り方）。
支援は「1 発の威力」と「撃つ回数」の両方を増やすので、倍率は両者の積で取る。

範囲・連鎖・貫通・送還の巻き添えも、燃焼の継続ダメージも全部数える
（`_apply_damage` を通る経路すべてに塔を渡した。燃焼は火を付けた塔の種類を
敵に持たせて返す）。撃破は最後に当てた塔の種類に付ける。

実測（big_tower vs support_mix、決着まで）::

    == big_tower ==   総ダメージ 35,652   総撃破 179
    塔           本数      与ダメ    占有率    撃破   1本あたり
    ARROW         23       4,643    13.0%      8        202
    CANNON        24       4,290    12.0%     24        179
    TESLA         20         840     2.4%      2         42
    BALLISTA      22      13,308    37.3%    145        605
    WATCHTOWER     6      12,571    35.3%      0      2,095

**監視塔が与ダメの 35.3%、1 本あたりでは全塔中トップ**。自分の撃破は 0。
旧観測では `DPS/コスト = 0.000` として渡していた塔がこれ。
構成比でも撃破数でも絶対に見えない数字で、**この 1 行のために作った**。

**⑤ 分布** — 主要指標に p10 / p50 / p90 を追加。

**⑥ 方策に依存しない定点観測** (`defense_probe`)

評価のたびに `tower_bench.defense_run` を固定ボット 3 種で回し、
**同じ金・同じ波での漏れ率**を記録する。方策と無関係なので、
`balance_fingerprint` と並べれば「バランスをいじったせいで変わった」が読める。
1 種 1.7 秒、3 種で 5 秒。

### 10-3. 敵の同時上限を 96 へ

`EnvConfig.max_enemies` で設定できるようにした。実測::

    2 人戦   同時最大 28 体   上限に触れない   3701 board-steps/s
    8 人戦   上限 48 で頭打ち                  1415
             上限 96 で最大 96 まで伸びる      1162（-18%）
             上限 160 で最大 129               1049（-26%）

2 人戦は 48 でも触れないので影響なし。頭打ちは 8 人戦だけ。
160 は割に合わないので 96 で止めた。

### 10-4. 途中で見つけた実バグ

- **ロールアウトバッファがチャンネル数 14・スカラー次元 210 を直書き**していた。
  観測を増やした瞬間に学習だけが落ちる（`could not broadcast (8,16,27,27)

どちらも「回してみないと分からない」類なので、**学習を 1 世代だけ回す通しテスト**を

## 8. 対戦経済の作り直しに合わせた変更（2026-09-04）

対戦の数値を全面的に組み直した（経緯は [VERSUS_ECONOMY_ja.md](VERSUS_ECONOMY_ja.md)）。
そのとき **報酬そのものは何も変えなくてよかった** ので、
「なぜ変えなくてよかったのか」と「代わりに何を変えたのか」を残す。

### 報酬を変えなかった理由

整形はすべて `_lead(mine, theirs, floor) = (mine-theirs)/(mine+theirs+floor)` という
**相対優位**で書いてあり、絶対値を報酬にしていない。だから経済のスケールが
何倍になっても式の意味が変わらない。

- `INCOME_FLOOR = 20` — 「開幕 5 対 5 で 1 差が 0.09」用の下駄。開始インカムは 5 のまま
- `THREAT_FLOOR = 300` / `PATH_FLOOR = 200` — 開幕（両者 0）で暴れないための下駄。
  盤面 21x21・塔 24 基は変えていない
- `W_LIFE` ほかの重み — ポテンシャル整形なので、重みを変えても最適方策は変わらない

### 1 項は経済側の修正で勝手に正しくなった

`MAX_LIFE_STOLEN = -0.05` は、旧仕様では **終焉騎を倒したときに**発動していた。
つまり守り側がどう打っても避けられない罰で、勾配としては信号ではなくノイズだった。
発動を「コアまで通されたとき」に直したので、**いま初めて学習可能な信号になっている**。
値は据え置きで妥当（ライフ 20 全部で -1.0 ＝ 主軸と同じ大きさ）。

### 代わりに直したもの ①: ヒューリスティックボットの閾値

`bots_heuristic.py` の判定が旧経済（送り最大 150 コイン）で刻まれた**絶対値**だった。

```python
income_target = 60.0      # ここまでは送りをインカム投資として優先
send_reserve  = 400.0     # 塔と強化のあと送りに回す下限
pressure_coins = 1500.0   # ここを超えたら重い送りで押す
if bd.coins[b] > 150: send[0]   # 守りボットは最安の送りを撃つだけ
```

指数で伸びる経済では、この手の定数は**数分で常に真になって分岐が死ぬ**。
実測すると 16 分時点のインカムが 410（設計上は 5,474）＝ 経済の 8% しか使えず、
18 段の梯子の下から 5 段目より上を一度も撃たなかった。
これはリーグの対戦相手・BC の教師・対称性チェックの測定器を同時に壊す。

判定をすべて相対量に置き換えた:

| 旧 | 新 |
|---|---|
| `income_target = 60` | 相手の平均インカムに遅れているか (`_rival_income`) |
| `send_reserve = 400` | 次に建てる / 強化する 1 手ぶんのコスト (`_defence_reserve`) |
| `pressure_coins = 1500` | 解禁済み最上位インカムモブ何体ぶんか (`_should_pressure`) |
| `coins > 150 → 最安を送る` | 予備費を引いた残りで `_invest_send` |

**`_invest_send` の導出。** ストックは毎秒 1 回復し消費はどれも 1 なので、
送れる回数は 1 秒 1 回で頭打ち。一方コインは毎秒 `income / 収入間隔` 増える。
だから **その額を 1 回で使い切れる、いちばん高いインカムモブ**が最適になる。
安いと送る回数が足りずコインが余り、高いと貯める時間ぶん送る回数が減るうえ
梯子は上ほどインカム比率が悪いので二重に損。
梯子は飛び飛びなので、貯まったコインを収入 1 回ぶんの時間で吐き出す項も足す。

途中で「ストックが余っているか」で判定する実装を試したが、
**毎秒 1 回しか行動しない以上ストックが減らない**ので、20 分ずっと走狗だけを
13,637 体送って終わった。導出をやり直した記録として残す。

直した後（4 人戦・18 分時点）:

| | 旧 | 新 |
|---|---|---|
| 守りボットのインカム | 234 | 348 |
| 送りボットのインカム | 466 | 2,035 |
| 到達した塔レベル | 4 | 5 |
| 送った種類 | 走狗のみ | 走狗〜熱塊（9 段） |

### 代わりに直したもの ②: γ を 0.997 → 0.999

§6-③ で挙げていた未解決論点。カリキュラム最終段を 12 分 → 20 分に伸ばしたので
悪化していた。実効視野は `1/(1-γ)` 手（1 手 = 1 秒）:

| γ | 実効視野 | 20 分（1,200 手）先の勝敗の重み |
|---|---|---|
| 0.997 | 333 手 = 5.5 分 | **0.027** |
| 0.999 | 1,000 手 = 16.7 分 | **0.301** |

このゲームの一番大事な判断（守りに使うか、送って収入を伸ばすか）は
10 分以上先に効くので、0.997 では視野の外にあった。

あわせて **割引率を 1 か所に統一**した。`reward.GAMMA` と `TrainConfig.gamma` が
ずれるとポテンシャル整形の「方策を変えない」保証が崩れるのに、
別々に書いてあって環境変数 `MAZEWARD_GAMMA` で片方だけ動かせた。

- `TrainConfig.gamma` の既定値を `reward.GAMMA` から取る
- 環境変数で上書きされたら起動時に `reward.GAMMA` へ代入し直す
- `shaping(..., gamma=GAMMA)` の**既定引数を廃止**。既定引数は import 時に
  評価されるので、代入し直しても反映されず黙ってずれる

### まだ解けていない: 行動レートが梯子の上を殺している

`DECISION_TICKS = 20`（1 秒に 1 手）なので、AI は**送りと建設を同じ秒に両立できない**。
実測した到達点:

| 条件 | 18 分時点のインカム |
|---|---|
| 送りだけに全行動（守り無し・撃破報酬も無し） | 2,780 |
| 実戦条件・送り特化 | 2,035 |
| 実戦条件・守り特化 | 348 |
| 経済モデル（行動レート無制限） | 9,956 |

一方、梯子の上位の解禁インカムは
鉄壁 2,520 / 天蓋 4,080 / 大祭司 6,480 / 大分裂体 10,200、終焉騎 5,000。
**上 4〜5 段は 20 分の AI 対戦では触れない**。人間は送りメニューを連打しながら
塔も置けるので届くが、AI 環境では死に札になっている。

取りうる手は 3 つ。どれも一長一短なので保留にしてある。

1. 梯子の上半分を圧縮する（コスト成長 1.6 倍 → 1.45 倍。Hypixel の実値）。
   人間の試合でも上位段が出やすくなるが、せっかく伸ばした幅が縮む
2. 1 手で「送り + 建設」を同時に出せるようにする（行動空間の変更）
3. `DECISION_TICKS` を 10 に下げる。エピソード長と学習時間がそのまま倍

### 追記: まとめ送りを入れて「行動レート」の論点を潰した

上で「まだ解けていない」としていた件。結論から言うと **1 手で複数体送れるようにした**。

- 行動ヘッド `send_n`（1〜30）を追加。払えない数は
  `min(ストック, コイン // コスト)` で黙って切り詰める。
  空振り扱いにすると「大きい数を選ぶこと自体」を怖がるようになるため
- 湧きは `SEND_STAGGER_TICKS = 4`（0.2 秒 = `COMBAT_DT`）ごとに 1 体ずつ。
  同座標に固めると範囲攻撃と連鎖が 1 塊に当たり、体数の意味が消える
- `MAX_ENEMIES` 96 → 256

**ただしこれは経済の上限を上げない。** 持続レートを縛っているのは行動数ではなく
**ストック回復（毎秒 1 体）**なので、まとめても送れる総数は変わらない。
実測でも送り特化ボットのインカムは 2,035 → 1,838 とほぼ動かなかった。
効くのは「空く手数」のほうで、恩恵を受けるのは
**建設と送りを両立したい方策**（＝学習した方策）。極端なボットには効かない。

計算コストも上がらない。送る総数を固定してまとめ方だけ変えた実測では、
まとめたほうが**速い**（30 秒に 1 回 30 体で 0.68 倍の時間）。
敵が途切れる時間ができるぶん、戦闘を回す幅 `en_count.max()` が縮むため。

梯子の上が届かない件は、まとめ送りではなく **梯子側を圧縮**して解決した
（コスト成長 1.6 → 1.45 倍、最上段 17,000 → 4,000／解禁 10,200 → 2,000）。
持続レートがストックで決まる以上、
**最上段は「毎秒 1 回の送りで到達しうるインカム」に合わせるしかない**。
詳細は [VERSUS_ECONOMY_ja.md](VERSUS_ECONOMY_ja.md) §3〜§4。

### 追記: Java 側のフォールバックボットも同じ理由で壊れていた

`HeuristicPolicy`（ブリッジが落ちているとき実ゲームを回す貪欲ボット）にも
旧経済の定数が残っていた。

```java
private static final int SEND_RESERVE = 40;   // 送るとき手元に残すコイン
private static final int STOCK_FLOOR  = 20;   // これだけ溜まるまで送らない
```

`STOCK_FLOOR` は「ストック消費 1〜5」時代に**重い送りを撃てる体にしておく**ための
待機だった。消費が全部 1 になったので理由ごと消えている。
`SEND_RESERVE = 40` は、いちばん安い強化（弓塔 27 コイン）と同じ桁なので、
**強化がコインを先に食い尽くして送りの条件が永久に立たない**。
実測で 25 分・インカム 22・送り 11 回・全員引き分けになっていた。

直したのは 4 点。順に測りながら決めた。

| # | 変えたこと | 結果（4 体対戦・25 分上限） |
|---|---|---|
| 0 | 直す前 | インカム 22 / 送り 11 / 引き分け |
| 1 | 予備費を「次の 1 手ぶんのコスト」に相対化 | 変わらず |
| 2 | ストックが溜まっていたら送りを先に見る | インカム 73 |
| 3 | 送りの**判定**からは予備費を外す（体数には残す） | 決着するが塔が 4〜10 基で固まる |
| 4 | 割り込みを**ストック満タン / 盤面を建て切った**ときだけに | インカム 331〜360・塔 24 基・9.1 分で決着 |

③ が肝で、**判定と体数で予備費の扱いを分ける**必要があった。
両方に効かせると分岐が立たず、両方外すとコインを全部送りに吸われて塔が建たない。

④ も測って決めた。半分（ストック 15）で割り込ませると、少しずつしか減らないので
送り分岐が毎秒立ち続け、塔が下限で固まる。満タン（30）だと
溜まるまで 30 秒かかるので、そのあいだ建設が手を持つ。
あわせて **盤面を 24 基まで建て切るまで強化しない** ようにした
（強化はいちばん安い段が常に手の届く額なので、建設と同列だと数が増えない）。

`gradle aiSim` が通るようになっている。
